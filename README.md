# Phoenix build times

How fast can a realistic Phoenix app compile and hot reload on the latest Erlang/OTP, Elixir and
Phoenix `main`, and what does it take to make it faster?

[`shop/`](shop/) is generated by [`bench/generate-app.sh`](bench/generate-app.sh): `phx.new`
(SQLite), `phx.gen.auth`, and 40 `phx.gen.live` resources in 8 contexts with 160 LiveView routes.
That makes 194 `.ex` files and 752 tests. Measured on an Apple Silicon laptop (12 cores).

## Findings

Every change that is measured, what it is worth, and why it works. "Repo" means this repository
uses it; "fork" links the branch with the change.

| # | finding | where | affects | before → after | why it helps | status |
|---|---|---|---|---|---|---|
| 1 | Compile deps in 4 OS processes | `MIX_OS_DEPS_COMPILE_PARTITION_COUNT=4` | cold | deps 16.6s → 8.9s (−46%) | dependencies compile in parallel instead of one by one | repo |
| 2 | Skip Erlang optimization passes in dev/test | `erlc_options` + `ERL_COMPILER_OPTIONS` | cold, warm | deps 8.8s → 5.2s, app 2.65s → 1.84s | 70-80% of each module's compile time is `beam_ssa_opt` and friends, which only make code faster at runtime | repo, prod builds refuse the flags |
| 3 | `module_definition: :interpreted` | `elixirc_options` (Elixir 1.20+) | cold | −6% app | module bodies are evaluated instead of compiled | repo |
| 4 | Router `group_by: :verb` | `use Phoenix.Router` | cold, warm | router compile −17% | one `__match_route__` function per verb instead of one huge function | repo |
| 5 | Shared route `prepare` | [phoenix#6888](https://github.com/phoenixframework/phoenix/pull/6888) | cold, warm | router compile −18% | 180 per-route closures become literals for one shared function | fork, PR open |
| 6 | Router routes as a binary, `__match_route__` via `apply` | [onnimonni/phoenix@router-faster-compile](https://github.com/onnimonni/phoenix/tree/router-faster-compile) | warm, hot reload | router compile 648 → 362ms, router type check 163 → 37ms; edit router 1.56 → 1.21s, edit LiveView 0.84 → 0.69s | `__routes__/0` returned a 180-struct literal that is slow to compile and type check; `call/2` destructured the union of every route's return type | fork, no PR yet |
| 7 | Type check cache for unchanged signatures | [onnimonni/elixir@faster-recompile](https://github.com/onnimonni/elixir/tree/faster-recompile) | warm, hot reload | edit LiveView 0.69 → 0.60s, core_components 0.94 → 0.83s, router 1.21 → 1.10s; hot reload 130 → 84ms | editing a LiveView re-type-checked the router (it refers to every LiveView). If the edited module's signatures (`ExCk` chunk) are unchanged, dependents without warnings reuse their previous result. Behaviour checks and `@after_verify` (`~p` route checks) still run | fork, no PR yet |
| 8 | macOS file watcher without latency | `config :phoenix_live_reload, :backend_opts, latency: 0.0, no_defer: true` | hot reload | 752 → 203ms (with #9) | FSEvents batches changes for up to 0.5s by default; saving a file took ~200-500ms to be noticed | repo |
| 9 | `live_reload: [interval: 0]` | endpoint config | hot reload | (with #8) | the browser waited 100ms before reloading | repo |
| 10 | Re-render LiveViews in place | `live_reload: [notify: [live_view: [...]]]` | hot reload | 203 → 179ms | connected LiveViews recompile and re-render with their current state: no page reload, no remount, form inputs survive | repo |
| 11 | Don't purge consolidated protocols on every reload | Phoenix CodeReloader passes `--purge-consolidation-path-if-stale` | hot reload | 153 → 130ms | Mix purged ~all consolidated protocols (18ms) and reloaded them on the next render, on every save | experiment only: needs a design that still purges when a protocol implementation changes |
| 12 | Clone `_build` and `deps` into new worktrees | `/bin/cp -c -R` (APFS) or `cp --reflink=auto` | cold | new worktree 10.7s → 2.4s | dependencies stay compiled; Mix only recompiles the app because the working directory changed | manual |
| 13 | Fix broken JS bundle | `shop/assets/package.json` | hot reload | LiveViews never connected | a `package.json` with `"type": "module"` in a parent directory made esbuild treat vendored `topbar.js` as ESM | repo |
| 14 | OTP master compiler crash on `decimal` | [erlang/otp#12121](https://github.com/erlang/otp/pull/12121) | cold | crash → builds | `beam_types:norm_number/1` converted huge integer bounds to floats | fork, PR open |

Measured and not worth it: `infer_signatures: false` (−3%), `debug_info: false` (−2%), more than
4 deps partitions (slower), loading LiveView modules from the checker's binary before
`@after_verify` (no wall-clock change), `mix compile --no-deps-check` (no change).

(Playwright's polling would add up to 100ms). Median of 15 edits to the login LiveView.

## Details

### Skipping Erlang optimizations (#2, #3)

```elixir
# shop/mix.exs
elixirc_options: elixirc_options(Mix.env())

defp elixirc_options(:prod), do: []

defp elixirc_options(_env) do
  [
    module_definition: :interpreted,
    erlc_options: [:no_ssa_opt, :no_copt, :no_bsm_opt, :no_bool_opt,
                   :no_share_opt, :no_recv_opt, :no_throw_opt]
  ]
end
```

`elixirc_options` only covers the app. [`devenv.nix`](devenv.nix) sets `ERL_COMPILER_OPTIONS` to
the same flags for dependencies. `shop/mix.exs` refuses `MIX_ENV=prod` builds while that variable
disables optimizations. All 752 tests pass on the unoptimized build.

### The router type check (#6, #7)

The router is the biggest module: 160 LiveView routes compile into a 1 MB `.beam`. Timing
`Module.Types.warnings/6` per function showed `call/2` taking ~120ms of the 149ms router check:
it pattern matches `__match_route__/3`, whose inferred return type is the union of ~180 different
literal tuples. Calling it through `apply/3` makes the result `dynamic()`. Each LiveView is a
runtime dependency of the router, so before #7 every LiveView edit type checked the router again.

The type check cache (#7) keeps correctness: renaming a route path (which leaves the router's
signatures unchanged) still reports `no route path for ShopWeb.Router matches "/catalog_alphas"`
from `~p`, because `@after_verify` callbacks always run. Elixir's `compile.elixir_test.exs` passes
(59 tests, one new). Four seed-dependent dependency-ordering tests in `dep_test.exs` and
`umbrella_test.exs` fail on OTP master with and without the change.

### Hot reload config (#8-10)

See [`shop/config/runtime.exs`](shop/config/runtime.exs). `LIVE_RELOAD_DEFAULTS=1` restores the
generated config and `LIVE_RELOAD_NO_NOTIFY=1` disables in-place re-rendering, for benchmarks.

### Mix startup (0.42s no-op floor)

| part | time |
|---|---|
| BEAM + Elixir boot | 0.16s |
| `deps.loadpaths` | 0.13-0.20s |
| ↳ `Mix.Dep.load_and_cache`: load ~70 modules and compile 47 deps' `mix.exs` | 0.11s |
| `compile.all` with nothing to do | 0.05s |

Caching the converged dependencies in `_build` (keyed on `mix.lock` and the `mix.exs` files)
could save ~0.1s on every Mix command. Not implemented.

### OTP compiler crash (#14)

OTP master (4ba5448, 2026-10-30) can't compile the `decimal` library:

```
internal error in pass beam_validator_strong: bad argument in float/1
  in call from beam_types:norm_number/1
```

`decimal` compares against `10^2000`, beyond the float range. The smallest module that crashes:

```erlang
f(I) when I < 1 bsl 1100 -> I;   % I is a number range starting beyond the float range
f(I) -> g(I).
g(0) -> 0;
g(I) -> g(I div 3).              % widening g/1's argument type hits norm_number/1
```

[`devenv.nix`](devenv.nix) builds the OTP and Elixir forks from source.

## Reproduce

```sh
devenv shell                       # Erlang/OTP + Elixir forks, built from source
bench/generate-app.sh shop         # regenerate the app (or use the committed one)
cd shop && ../bench/measure.sh . 7

bench/release-shell.sh 'cd shop && ../bench/measure.sh . 5'   # released toolchain

# hot reload: run the server and the editor, then bench/hot-reload/measure.js in Playwright
(cd shop && mix phx.server) & elixir bench/hot-reload/editor.exs shop
```
